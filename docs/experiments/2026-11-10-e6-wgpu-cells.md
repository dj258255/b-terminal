# 실험 E6: wgpu로 200×60 화면을 통째 그리면 CPU `draw_grid`보다 짧은가

- 날짜: 2026-11-10
- 관련 이슈: [#347](https://github.com/dj258255/b-terminal/issues/347), [ADR-035](../decisions.md#adr-035-셀-렌더러는-wgpu로-창-없이-먼저-만들고-텍스처는-srgb가-아닌-꼴로-두며-앱-연결은-다음-판에-한다), [실험 E1](2026-11-05-e1-cpu-frame-time.md)
- 커밋: feature/wgpu-cells 브랜치(이 실험을 넣은 PR)
- 원자료: 아래 "결과"의 출력이 전부다

## 가설

> 같은 200×60 화면을 wgpu 렌더러가 텍스처에 그리는 시간(인스턴스 준비 + 제출부터 GPU가 끝낼 때까지)이 CPU `draw_grid` 통째 그리기보다 짧다.

## 이 실험이 정할 것

> 짧으면 다음 판에서 창 surface에 직접 그리는 연결로 간다. 길면 아틀라스·인스턴스 만들기를 먼저 손본 뒤 다시 잰다. 빠르지 않아도 결과로 남긴다(이슈 #347의 결정 기준).
> 읽어 내기(`read_pixels`)는 창에 직접 그리면 없어질 시험용 비용이라 따로 적는다.

## 조건

- 기기: Apple M2 Pro Mac(arm64), macOS 26.3.1, Rust 1.96.0 `--release`, wgpu 30.0.1(Metal). `GpuRenderer`가 연 어댑터 이름은 `Apple M2 Pro`
- 글꼴: 넣어 둔 JetBrains Mono, 배율 2.0, 셀 16×35px, 화면 3200×2100px(약 672만 픽셀). **실험 E1은 Menlo 14pt(셀 17×33, 3400×1980)였다.** 글꼴이 달라 E1의 숫자와 바로 견주지 않는다
- 내용: E1과 같은 문자열(60줄 모두 색 글자 + 한글 4자 + 상자 선·반칸 블록 + x 120개), 커서 블록 켬. 상자 선·블록(U+2500~259F)은 CPU가 직접 그리고 GPU는 글꼴 글리프로 그린다
- 한 번 그려 글리프 캐시와 아틀라스를 채운 뒤 20회 반복(첫 회는 잰 값에서 뺐다). 20회가 한 번의 실행이고, 실행을 세 번 했다
- CPU: 버퍼 지우기 + `draw_grid`. E1과 달리 VT 해석(`Emulator::feed`)은 넣지 않는다(화면 값은 한 번만 만든다). 버퍼는 한 번 잡아 재사용한다
- GPU: 아래 지표 세 가지. 인스턴스 버퍼와 텍스처는 처음 한 번만 만든다

## 지표 정의

- CPU: `Canvas::clear` + `draw_grid`의 벽시계 시간(`Instant`)
- GPU 준비: 격자를 인스턴스 목록으로 바꾸기 + 새 글리프 올리기 + 인스턴스 버퍼 쓰기(CPU 쪽 시간)
- GPU 제출~끝: 그리기 명령 제출부터 `device.poll(wait)`가 돌아올 때까지
- GPU 읽어 내기: 텍스처를 버퍼로 복사해 `Vec<u32>`로 바꾸기까지. 시험용이며 창에 직접 그리면 없다
- 모두 20회의 최소·중앙값·최대. 한 실행에 20회뿐이라 비율이 아니라 값으로 적는다

## 결과

`cargo test -p bt-gpu --release --test gpu -- --ignored --nocapture e6`을 세 번 돌렸다(실행마다 중앙값을 적는다). 값은 ms, 괄호는 최소~최대.

| 실행 | CPU draw_grid | GPU 준비 | GPU 제출~끝 | GPU 읽어 내기 | GPU 합계(렌더+읽기) |
|---|---|---|---|---|---|
| 1 | 7.63 (7.39~11.15) | 0.62 (0.57~0.66) | 1.25 (1.19~1.35) | 2.27 (1.93~2.87) | 4.10 (3.71~4.88) |
| 2 | 7.96 (7.20~10.60) | 0.62 (0.56~1.33) | 1.30 (1.20~2.63) | 2.35 (2.18~5.78) | 4.30 (3.99~7.78) |
| 3 | 11.82 (7.44~21.47) | 0.65 (0.61~5.56) | 1.46 (1.30~10.39) | 4.07 (3.13~20.12) | 6.77 (5.81~31.13) |

준비와 제출~끝 중앙값의 합(읽기 제외)은 1.87, 1.92, 2.11ms로 CPU 중앙값의 약 1/4~1/6이다. 읽기까지 더하면 4.10~6.77ms로 CPU보다 짧았다(3/3).

원자료: 이 표의 출력(작업 폴더의 `i347/e6.txt`, 저장소에는 넣지 않았다).

## 예상과 다른 점

- 읽어 내기가 그리기 자체(제출~끝)보다 길었다(2.27 대 1.25ms). 창에 직접 그리면 이 비용은 없어지지만, 지금 수치만으로 "GPU 합계"를 프레임 시간으로 읽으면 안 된다.
- 3회 실행은 CPU 중앙값도 11.82ms로 올랐고 최대값이 GPU 쪽에서도 10~31ms로 튀었다. 같은 시각에 다른 작업(다른 에이전트의 빌드일 수 있다)이 돌았을 수 있으나 확인하지 않았다. 원인을 가리지 않았다.
- E1은 CPU 6.7~7.3ms였고 이번 CPU 값은 7.6~8.0ms(실행 1·2)다. 글꼴·셀 크기·VT 해석 유무가 달라 같은 조건이 아니다.

## 배제한 원인과 남은 가능성

- 글리프 래스터와 아틀라스 채우기는 첫 회에서 끝나 잰 값에 들지 않는다(처음 그릴 때의 시간은 재지 않았다).
- GPU 쪽 `제출~끝`에는 폴링 대기와 Metal 명령 제출이 들어 있어 순수 GPU 실행 시간이 아니다(타임스탬프 쿼리로 재지 않았다).
- 인스턴스 수(글리프·사각형 개수)는 세지 않았다.
- 상자 글자를 GPU가 글리프로 그려 CPU와 일이 다르다. 상자 선 칸을 뺀 화면으로 다시 재지 않았다.
- 창 surface에 올리는 시간(present), 입력부터 화면까지의 지연, 부분 다시 그리기(E2)와의 비교는 재지 않았다. 앱에 연결하지 않았다.

## 결론과 적용 범위

- 이 기기(Apple M2 Pro, Metal)·이 글꼴·이 화면 크기·이 실행 3회에서 가설이 맞았다: 그리기(준비 + 제출~끝)는 CPU의 약 1/4~1/6이었다.
- 한 기기, 세 실행, 한 화면 내용이다. 다른 GPU·소프트웨어 어댑터, 더 큰 화면, 스크롤 중의 연속 프레임, 창에 올리기까지 포함한 값은 모른다.
- 읽어 내기를 빼지 않으면 GPU 합계도 CPU보다 짧았지만(4.1~6.8 대 7.6~11.8ms), 앱이 쓸 경로(창에 직접 그리기)의 값이 아니다.

## 다음에 확인할 것

- 창 surface(또는 IOSurface)에 직접 그릴 때 present까지의 시간. 주 세션이 창에서 잰다.
- E2의 바뀐 줄 1줄 그리기(CPU)와 GPU 통째 그리기를 견준다.
- 부분 갱신 없이 통째로 그리는 GPU가 CPU 부분 갱신(E2)보다도 짧은지.
- 타임스탬프 쿼리로 GPU 실행 시간만 재고, 상자 선을 같은 방식으로 그려 일을 맞춘다.
