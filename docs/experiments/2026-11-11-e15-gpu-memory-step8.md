# 실험 E15: GPU 길 그림판 수와 창마다 GPU 텍스처

- 날짜: 2026-11-11(주 세션이 잼)
- 관련 이슈: [#398](https://github.com/dj258255/b-terminal/issues/398)(추적), [#399](https://github.com/dj258255/b-terminal/issues/399), [#400](https://github.com/dj258255/b-terminal/issues/400), [실험 E14](2026-11-11-e14-gpu-memory-step7.md)
- 원자료: 주 세션 scratchpad의 `e13/`, `e15/`, `e15a/` 폴더(`vmmap -summary` 출력, debug 로그). 저장소에는 넣지 않는다
- 구현은 서브에이전트가 각자 worktree에서 했다

## 조건(공통)

- 기기: Apple M2 Pro, macOS 26, 내장 화면(120Hz), `--release`, 창 1000×680pt(2000×1360px)
- 격리: `HOME`을 빈 폴더로, `TMPDIR`을 짧은 경로로
- 메모리: `vmmap -summary`의 Physical footprint. 앱을 띄워 60줄을 그린 뒤 창 1개, `btctl new --window`로 창 2개
- 기준 빌드: origin/main b9c902d(0.36.0)

## 기준: 0.36.0의 GPU 길과 CPU 길(여섯 쌍, 1분 부하 3.5~8.3)

| | 창 1 footprint | 창 1 IOSurface | 창 2 footprint | 창 2 IOSurface |
|---|---|---|---|---|
| GPU 길 | 92.4~102.5MB | 21.0MB 세 번, 31.5MB 세 번 | 149.3~169.9MB | 42.1MB 두 번, 52.6MB 세 번, 63.1MB 한 번 |
| CPU 길(`BT_GPU=0`) | 80.5~81.7MB | 31.4MB(여섯 번) | 126.6~127.7MB | 62.8MB |

- CPU 길과 견준 GPU 길 창 1(같은 회차 4번째): owned unmapped (graphics) +18.7MB, MALLOC_SMALL +4.2MB, IOAccelerator +1.1MB, IOSurface −10.4MB(그 회는 2장)
- 창 하나를 더할 때(GPU 길): IOSurface +21.1MB, owned unmapped graphics +18.7MB, MALLOC_LARGE +10.4MB, MALLOC_SMALL +4.8MB
- CPU 길의 IOSurface 31.4MB는 앱이 쓰는 IOSurface 셋이다(GPU 길 그림판과 다른 것).

## A. 그림판이 3장 몫으로 남는 까닭(#399)

### 가설

> 창을 열 때 surface를 여러 번 설정(`configure`)하거나, 첫 프레임 전에 크기가 바뀌거나, 그림판 수를 정하기 전에 첫 그림판을 얻으면, CAMetalLayer가 옛 그림판을 놓기 전에 새로 잡아 3장 몫이 남는다.

### 방법

- 에이전트가 b9c902d 빌드 하나로 쟀다(코드 변경 없음, 1분 부하 11.8~15.7로 높음).
  - `RUST_LOG=b_terminal=debug,wgpu_hal=debug`로 surface 설정과 프레임 로그를 남겼다.
  - 창 1·창 2 vmmap 여섯 회
  - 창 1개를 띄워 약 0.4초 간격으로 IOSurface를 시간순으로 찍었다(입력 뒤 여덟 회, 입력 없이 14초 여섯 회).
  - `BT_FRAME_LATENCY=2`로 같은 측정 여섯 회

### 결과

- 창 1 IOSurface는 여섯 회 가운데 21.0MB가 다섯 번, 31.5MB가 한 번이었다. 창 2는 42.1MB 세 번, 52.6MB 두 번, 63.1MB 한 번이었다.
- surface 설정은 창마다 한 번뿐이었다(크기 2000×1360, 지연 1). 2장 회와 3장 회의 순서가 같았다(첫 프레임은 가려져 건너뜀, 그다음부터 올림).
- wgpu-hal 30 Metal은 설정 안에서 그림판 수를 크기보다 먼저 정한다. 첫 그림판을 얻기 전이다.
- 시간순 표본
  - 입력 없이 두면 IOSurface는 10.5MB(1장)다. 그림판은 필요할 때 늦게 만들어진다.
  - 화면을 바꾸는 입력 뒤 여덟 회 가운데 여섯 회는 21.0MB로 바로 안정됐다. 두 회는 31.5MB까지 올랐다가, 다음 입력으로 다시 그리자 21.0MB로 내려왔다.
  - 입력 없이 14초 둔 회 가운데 끝까지 잰 네 회 중 한 회는 31.5MB를 내내 유지했다. 추가 한 장은 스스로 풀리지 않고 다음 올리기에서 풀린다.
- 지연 2(그림판 3장)에서도 여섯 회 가운데 한 회가 42.1MB(4장 몫)였다. "정한 수 + 1장"이 생기는 일은 지연 1만의 일이 아니다.
- 단서(상관만 봄): 3장이 남은 회는 마지막 프레임의 얻기가 0.5ms 안팎이었고, 2장인 회는 0.03~0.06ms였다.

### 판정

까닭을 확정하지 못해 고치지 않는다.
- 배제한 가설: 설정 여러 번, 첫 프레임 전 크기 바뀜, 첫 그림판 뒤에 수를 정함.
- 배제하지 못한 것: 가려짐·보임 전환(모든 회의 로그 순서가 같아 가르지 못함).
- 추가 한 장은 CAMetalLayer 쪽에서 잠깐 생겨 다음 올리기까지 남는 것으로 보인다. 앱의 설정이 무시된 것은 아니다.
- 앱 쪽 손잡이는 찾지 못했다.
  - 레이어를 직접 다루려면 `unsafe`가 필요하다.
  - 가만히 있을 때 한 프레임 더 올리는 길은 "바뀐 것이 없으면 그리지 않는다"와 어긋나고, 풀리는지도 재지 않았다.
- 남은 후보(재지 않음): 마지막 프레임의 얻기 대기가 추가 한 장을 만드는지 `FramePacer`로 가르기, wgpu가 그림판을 쥐는지 가르기.

## B. 창마다 GPU 텍스처(#400)

### 가설

> 창마다 GPU 텍스처 18.7MB 가운데 아래층(10.88MB)을 뺀 7.8MB는 대부분 아틀라스다. 이모지를 쓰지 않는 창도 색 아틀라스(1024×1024 RGBA, 4MiB)를 쥔다.

### 방법

- 에이전트가 창 하나의 GPU 자원을 형식·크기에서 바이트로 세는 `GpuRenderer::gpu_memory()`를 만들었다. 창 없는 시험에서 2000×1360 글자 화면 한 장을 그린 뒤의 값을 냈다.
- 가장 큰 덜어낼 몫(색 아틀라스)을 이모지를 처음 볼 때 256×256으로 잡게 했다. 모자라면 두 배씩 큰다.
- 주 세션이 실제 창에서 기준 빌드와 번갈아 쟀다.
  - vmmap 네 쌍
  - 이모지 화면 세 장면
  - 탭 열고 닫기 두 쌍
  - 1분 부하 7~18(다른 에이전트가 창을 띄워 재는 중)

### 결과

**내역(창 없는 시험, 요청한 크기)**

| 항목 | 고치기 전 | 고친 뒤 |
|---|---|---|
| 아래층 텍스처 | 10,880,000B | 같음 |
| 회색조 아틀라스(1024², R8) | 1,048,576B | 같음 |
| 색 아틀라스 | 4,194,304B(1024², RGBA) | 4B(1×1, 이모지를 볼 때 256²부터) |
| 인스턴스·유니폼 버퍼 | 약 2.4KB | 같음 |
| 합 | 약 16.1MB | 약 11.9MB |

- vmmap 18.7MB와 센 합 16.1MB의 차이 약 2.6MB는 설명하지 못했다(드라이버 정렬·여분, 파이프라인으로 짐작, 재지 않음).

**실제 창(네 쌍)**

| | 기준(b9c902d) | 이 변경 |
|---|---|---|
| owned unmapped graphics 창 1 / 창 2 | 18.7 / 37.4MB | 14.7 / 29.4MB |
| footprint − IOSurface 창 1 | 69.8~71.5MB | 66.2~67.8MB |
| MALLOC_LARGE 창 1 | 15.8MB | 15.8MB |

- 창마다 GPU 텍스처가 4.0MB 줄었다.
- CPU 쪽 색 아틀라스 사본 4MiB는 footprint에 드러나지 않았다(MALLOC_LARGE 그대로). 0으로 잡은 페이지는 쓰기 전까지 물리 메모리를 쓰지 않기 때문으로 본다.
- 이 변경의 넷째 회는 창 2가 열리지 않아(`btctl`이 소켓을 찾지 못함) 창 2 값을 버렸다.
- 화면: 이모지(😀🎉🚀 ✅ 👍🏽 🇰🇷 👨‍👩‍👧)와 한글이 든 장면을 한 칸, 오른쪽으로 나눔, 나눈 칸을 닫음의 세 장면으로 찍었다. 기준과 다른 픽셀이 0이었다.
- 통째 프레임(탭 열고 닫기 두 쌍)
  - 그리기 중앙값: 1.54 / 1.43ms → 1.33 / 1.39ms
  - 층 올리기 중앙값: 작은 변경 0.54 / 0.50 → 0.47 / 0.49ms, 큰 변경 1.12 / 1.17 → 0.98 / 0.96ms
  - 늘지 않았다.
- 처음 이모지를 그리는 프레임(에이전트, 창 없음, release, 15회 중앙값, 부하 40~55)
  - 1.35ms → 1.41~1.48ms
  - 4MiB를 처음 볼 때 한꺼번에 잡는 중간판은 2.20~2.30ms였다. 그래서 256부터 시작한다.

### 판정

넣는다.
