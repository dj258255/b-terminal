# 실험 E1: CPU 렌더러로 200×60 화면을 Retina에서 전체 다시 그리면 8ms 안에 끝나는가

- 날짜: 2026-11-05
- 관련 이슈: [#5](https://github.com/dj258255/b-terminal/issues/5), [ADR-002](../decisions.md#adr-002-렌더러는-cpusoftbuffer--fontdue로-시작한다)
- 커밋: 971bffe 위의 feature/cpu-renderer 브랜치
- 원자료: 아래 "결과"의 출력이 전부다

## 가설

> 200×60 셀 화면을 화면 배율 2.0으로 버퍼 전체에 다시 그려도 한 프레임이 8ms 안에 끝난다(120Hz 화면의 한 프레임).

## 이 실험이 정할 것

> 맞으면 GPU 렌더러를 미루고 전체 다시 그리기로 간다. 틀리면 바뀐 줄만 그리기를 먼저 하고, 그래도 넘으면 GPU 이슈를 연다.

## 조건

- 기기: Apple Silicon Mac(arm64), macOS 26.3.1, Rust 1.96.0 `--release`
- 글꼴: Menlo 14pt × 2.0 = 28px, 셀 17×33px, 화면 3400×1980px(약 670만 픽셀)
- 내용: 60줄 모두 색 글자 + 한글 4자 + 상자 선·반칸 블록 + x 120개. 커서 블록 켬
- 한 번 그려 글리프 캐시를 채운 뒤 20회 반복. 한 회는 VT 해석(`Emulator::feed`) + 화면 값 꺼내기 + 버퍼 지우기 + 격자 그리기다. 창에 올리는 시간(softbuffer present)은 들어가지 않는다

## 지표 정의

- 프레임 시간: 위 한 회의 벽시계 시간(`Instant`). 20회의 최소·중앙값·최대

## 결과

`cargo test -p bt-render --release --test render -- --ignored --nocapture`를 세 번 돌렸다.

| 회 | 최소 | 중앙값 | 최대 |
|---|---|---|---|
| 1 | 6.70ms | 6.99ms | 21.39ms |
| 2 | 6.90ms | 7.30ms | 22.72ms |
| 3 | 6.79ms | 7.11ms | 17.75ms |

## 예상과 다른 점

- 중앙값은 8ms 안이지만 여유가 1ms 남짓이다. VT 해석까지 넣은 값이라 그리기만 따지면 더 짧다(따로 재지 않았다).
- 최대값이 17~23ms로 튄다. 테스트 실행기의 다른 스레드나 메모리 할당(매 회 버퍼를 새로 잡는다)일 수 있다. 원인을 가리지 않았다.

## 배제한 원인과 남은 가능성

- 글리프 래스터 시간은 첫 회에서 캐시를 채워 뺐다.
- 실제 창에서는 present 시간이 더해진다. 재지 않았다.

## 결론과 적용 범위

- 이 기기·이 글꼴·이 화면 크기에서는 가설이 맞았다(중앙값 7.0~7.3ms, 3/3회). GPU 렌더러는 미룬다.
- 화면이 더 크거나(5K 전체 화면) 느린 기기에서는 넘을 수 있다. 바뀐 줄만 그리기를 다음 단계로 둔다.

## 다음에 확인할 것

- 실제 창에서 present 포함 시간, 그리고 키 입력부터 화면까지의 입력 지연.
- 최대값이 튀는 원인(버퍼 재사용으로 줄어드는지).
