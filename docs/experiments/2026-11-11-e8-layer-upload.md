# 실험 E8: 층을 바뀐 사각형만 올리면 덧그림이 켜진 프레임이 CPU 길보다 빨라지는가

- 날짜: 2026-11-11(만든 날, 주 세션이 같은 날 잼)
- 관련 이슈: [#358](https://github.com/dj258255/b-terminal/issues/358), [실험 E7](2026-11-11-e7-gpu-window.md), [ADR-037](../decisions.md)
- 원자료: 주 세션 scratchpad의 `e8/` 폴더(회마다 로그). 저장소에는 넣지 않는다

## 가설

> 층을 앞서 올린 것과 견줘 달라진 사각형만 올리면 시나리오 B(진행 막대로 매 프레임 통째)에서 GPU 길의 "올리기까지" 중앙값이 CPU 길보다 짧아진다. A와 C는 E7과 비슷하게 유지된다. 견주기 비용(창 없이 21.76MB에 약 0.8~0.9ms)이 B의 줄어든 몫을 얼마나 깎는지도 본다.

## 이 실험이 정할 것

> B에서 다섯 쌍 모두 GPU 길의 중앙값이 CPU 길보다 짧으면 ADR-036의 "기본을 GPU로 바꿀 조건" (1)을 채운 것으로 본다. 아니면 내역(`층 올리기`, 올린 바이트, 얻기·인코딩·제출·올리기)으로 어디서 막히는지 적는다. 이 실험은 기본을 바꾸지 않는다.

## 조건

E7과 같다. 바꾼 것은 앱의 층 올리기(ADR-037)뿐이다.

- 기기: Apple Silicon Mac(arm64), macOS, `--release`, 내장 화면, 창 1000×680pt(2000×1360px), `window-colorspace` 기본
- 격리: `HOME`을 빈 폴더로, `TMPDIR`을 짧은 경로로
- 바꾼 변수: 그리기 길 하나(CPU = 환경 변수 없음 / GPU = `BT_GPU=1`). 두 조건을 번갈아 다섯 번씩
- 시나리오 A·B·C는 E7과 같다(A: 맨 윗줄만 0.2초마다, B: 진행 막대 OSC 9;4를 켠 같은 갱신, C: 0.2초마다 37줄 전부 다시 찍기, 덧그림 없음)
- 아무 설정도 주지 않는다. `CPU 길로 그린다` 줄이 나온 회는 버린다

## 지표 정의

E5·E7과 같다(프레임마다 한 줄, 한 회의 중앙값, 다섯 회의 중앙값). GPU 길의 내역이 늘었다.

```
다시 그리기: 통째 N줄 그리기 …ms, 올리기까지 …ms (GPU: 층 올리기 …(…바이트) 준비 … 제출·올리기 … = 얻기 … 인코딩 … 제출 … 올리기 …, Presented)
```

- `층 올리기 X(Y바이트)`: 견주기와 `write_texture`에 든 시간과 올린 바이트. 앞 버전은 B에서 21,760,000바이트였다.
- `= 얻기 … 인코딩 … 제출 … 올리기 …`: `제출·올리기`를 넷으로 나눈 것. 얻기는 `get_current_texture`(`Fifo`에서 화면 주사율을 기다릴 수 있다).
- 긴 프레임(C에서 E7이 본 16~25ms): 그 프레임의 넷 중 어느 것이 큰지 본다. 아래 8번.

## 잴 명령

주 세션이 창을 띄워 잰다. 이 문서를 쓴 에이전트는 창을 띄우지 않았다.

1. 빌드: `cargo build --release -p bt-app`
2. CPU 길: `RUST_LOG=debug HOME=<빈 폴더> TMPDIR=/tmp/bt ./target/release/b-terminal 2> e8-cpu-<시나리오>-<회>.log`
3. GPU 길: 위와 같고 `BT_GPU=1`을 더한다(로그 이름은 `e8-gpu-…`)
4. 창 크기를 1000×680pt(2000×1360px)로 맞춘다.
5. 시나리오 A / B / C의 셸 명령은 E7 문서의 것과 같다(`btctl send`로 보낸다).
6. 중앙값: E7 문서 7번과 같은 `grep`·`sed`·`awk`. A는 `바뀐 줄 1줄`, B·C는 `통째` 또는 줄이 많은 프레임(C는 `바뀐 줄 3[0-9]줄|통째`).
7. B의 올린 바이트 중앙값: `grep '통째' e8-gpu-B-<회>.log | sed -E 's/.*\(([0-9]+)바이트\).*/\1/' | sort -n | awk '{a[NR]=$1} END {print a[int((NR+1)/2)]}'`
8. 긴 프레임: `awk` 등으로 `올리기까지`가 10ms 넘는 줄을 뽑아 `얻기 …`가 큰지(그림판 대기), `제출`·`올리기`가 큰지, 둘 다 작은데 줄이 길면 앱 쪽 일인지 적는다.
   `grep -E '올리기까지 ([1-9][0-9]|[0-9]{3,})\.' e8-gpu-C-<회>.log`
9. 창 없이 견주기 비용 확인(에이전트가 한 번 잰 값과 같은 명령): `cargo test -p bt-gpu --release --test compose -- --ignored --nocapture upload_cost`

## 창 없이 확인한 것(에이전트, 한 번 잰 값)

- 진행 막대처럼 한 곳만 바뀌는 층, 막대가 줄어드는 층, 위층이 비는 층, 비었다가 다시 켜지는 층, 아래층 한 곳이 바뀌는 층을 차례로 합친 프레임이 모두 CPU 프레임과 같았다(`partial_layer_upload_keeps_every_frame_equal_to_the_cpu_frame`).
- 2000×1360 두 층, `compose`의 층 올리기 시간 중앙값(Apple M2 Pro, `--release`, 한 번 잰 값): 진행 막대 모양 0.912ms(888바이트), 덧그림 없이 층 그대로 0.827ms(0바이트), 위층이 통째 바뀜 3.833ms(10,880,000바이트).
- 창 surface(`present`)는 창 없이 시험할 수 없어 시험하지 않았다.

## 결과

주 세션이 잼(2026-11-11, Apple M2 Pro, 격리한 실제 창 1000×680pt = 2000×1360px, 37줄, `--release`, E7과 같은 스크립트). 길마다 번갈아 다섯 회씩. 값은 한 회 안 프레임들의 "올리기까지" 중앙값(ms). A는 바뀐 줄 1줄 프레임, B는 통째 프레임, C는 바뀐 줄 30줄 이상 프레임만 셌다. 모든 회에서 GPU 길은 CPU로 돌아가지 않았다.

| 회 | A CPU | A GPU | B CPU | B GPU | C CPU | C GPU |
|---|---|---|---|---|---|---|
| 1 | 1.94 | 0.53 | 2.50 | 1.87 | 3.18 | 0.35 |
| 2 | 2.01 | 0.52 | 2.37 | 2.05 | 3.08 | 0.35 |
| 3 | 1.96 | 0.50 | 2.94 | 2.11 | 3.25 | 0.34 |
| 4 | 1.88 | 0.52 | 3.07 | 2.20 | 3.16 | 0.34 |
| 5 | 1.84 | 0.53 | 2.97 | 2.07 | 3.23 | 0.34 |

- B: **다섯 쌍 모두 GPU가 짧다**(E7에서는 GPU 4.82~5.60으로 모두 길었다). GPU 한 프레임 내역 예: `층 올리기 1.31(0바이트) 준비 0.15 제출·올리기 0.23`. 진행 막대가 같은 값이면 올린 바이트가 0이고, 층 올리기 시간의 대부분은 견주기다. 막대 값이 바뀐 프레임은 48000바이트였다.
- C: GPU 회별 최대가 0.96~6.45(E7은 16~25ms 프레임이 다섯 회 중 네 회).
- 10ms 넘는 GPU 프레임(모든 로그 합쳐): (1) 창을 띄운 직후 첫 통째 프레임 — 층 21760000바이트를 올리고 9~12ms, 그 뒤 `Skipped("창이 가려졌다")`(창이 아직 화면에 보이지 않음). (2) 바뀐 줄 프레임 두 개 — 그림판 얻기(`get_current_texture`) 11.76·16.17ms. (3) B의 한 프레임 — 얻기 8.75ms. E7의 긴 프레임은 `Fifo`에서 다음 그림판을 기다리는 것으로 보인다(이 세 프레임에서 확인).
- 원자료: scratchpad `e8/`의 `{cpu,gpu}-{row,progress,screen}-{1..5}.log`.

## 다음에 확인할 것

- 견주기 비용(약 1.3ms, 실제 창): 앱이 "층 입력이 같다"고 알려 견줌을 건너뛰기
- 그림판 얻기 대기: 얻기를 기다리지 않는 길(그림판이 없으면 그 프레임을 미루기) 또는 `desired_maximum_frame_latency`를 바꿔 다시 재기
- 창이 가려진 첫 프레임에 층을 올린 뒤 건너뛰는 것
