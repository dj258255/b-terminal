# 실험 E21: 칸마다 셰이더의 텍스처를 줄인 뒤의 메모리·화면·프레임 시간

- 날짜: 2026-11-12(주 세션이 잼)
- 관련 이슈: [#444](https://github.com/dj258255/b-terminal/issues/444)(추적), [#445](https://github.com/dj258255/b-terminal/issues/445), 앞 실험 [E20](2026-11-12-e20-pane-shaders.md)
- 원자료: 주 세션 scratchpad의 `e21/` 폴더(측정 스크립트, 화면, 로그). 저장소에는 넣지 않는다

## 가설

> 마지막 셰이더 패스를 대상의 칸 사각형에 곧바로 그리고 같은 크기 칸끼리 중간 텍스처를 나눠 쓰면, 셰이더를 건 창의 footprint가 줄고 화면은 0.45.0과 한 픽셀도 다르지 않다.

## 조건

- E20과 같다: Apple M2 Pro 내장 120Hz, macOS 26, `--release`, 저전력 모드 켜짐, 창 2000×1360px, `HOME`·`TMPDIR` 격리, 회마다 새로 띄움
- 칸마다 `clear; echo pane`을 보내고 `btctl wait`로 `pane`을 기다린 뒤 3초 뒤에 찍었다
- 셰이더: E20의 시간에 따라 바뀌지 않는 셰이더(가장자리 청록, 초점 없는 칸 빨강, 커서 둘레 노랑)
  - 같은 셰이더를 `fragCoord` 대신 `gl_FragCoord.xy`로 쓴 것(직접)
  - 둘을 잇달아 건 것(셰이더 둘, 가운데 패스 길)
- 비교: 0.45.0(7de1881)과 새 빌드(#445 에이전트 커밋)를 같은 시간대에 번갈아 쟀다(1분 부하 2.4~4.1)

## 결과

### 메모리(footprint, vmmap)

| 장면 | 0.44.0(E20) | 0.45.0 | 새 빌드 |
|---|---|---|---|
| 셰이더 멈춤, 칸 하나 | 107.5~108.8MB | 121.4~121.5MB | 110.0~110.4MB |
| 셰이더 멈춤, 칸 셋 | 119.1~120.6MB | 157.8~158.3MB | 141.9~143.1MB |
| 셰이더 `always`, 칸 하나 | 106.2~106.7MB | 141.6~142.0MB | 128.2~128.4MB |
| 셰이더 `always`, 칸 셋 | 129.0~129.8MB | 191.0~191.5MB | 168.5~169.3MB |
| `gl_FragCoord` 직접, 칸 하나 | | 121.6MB | 111.0MB |
| `gl_FragCoord` 직접, 칸 셋 | | 157.6MB | 143.2MB |
| 셰이더 둘, 칸 하나 | | 121.8~122.5MB | 121.6MB |
| 셰이더 둘, 칸 셋 | | 159.2MB | 152.1MB |

- 범위는 두 회 이상, 값 하나는 한 회다. `always`는 화면 비교 회와 프레임 시간 회를 합쳐 네 회다.
- 셰이더 하나일 때는 줄어든 양이 다음과 같다.
  - 칸 하나: 멈춤 약 11MB, `always` 약 13MB. 칸 크기 한 장(2000×1272px 약 10.2MB)이 빠진다는 셈과 맞다.
  - 칸 셋: 멈춤 약 15~16MB, `always` 약 22~23MB
- 셰이더 둘·칸 하나는 앞·뒤 두 장이 모두 필요해 줄지 않았다(셈과 같다).
- 0.44.0(창 전체에 셰이더 한 번)과 견주면 다음만큼 남는다.
  - 칸 하나: 멈춤 +2MB 안팎
  - 칸 셋: 멈춤 +22MB 안팎

### 화면

- 0.45.0과 새 빌드가 모든 장면에서 다른 픽셀 0이었다(기준끼리도 0).
  - 셰이더 멈춤·`always`: 칸 하나·셋, 두 회씩
  - `gl_FragCoord` 직접: 칸 하나·셋
  - 셰이더 둘: 칸 셋, 그리고 칸 하나의 옛 화면이 아닌 회
- 셰이더 둘·칸 하나에서 새 빌드 세 회 가운데 두 회는 셸이 `pane`을 찍은 뒤에도 화면이 그 앞 프레임에 멈춰 있었다.
  - 그 두 회는 footprint도 약 10MB 컸다.
- 같은 일을 다시 재현해 보니 이번 변경과는 상관이 없었다.
  - 0.45.0에서도 셰이더 하나·둘 각각 네 회 가운데 한 회씩 같은 화면이 나왔다.
  - 셰이더 없는 새 빌드에서도 다섯 회 가운데 세 회, wait 종료 코드를 찍은 네 회 가운데 한 회 같은 화면이 나왔다. 그 회의 footprint는 96.3MB로, 다른 회는 86MB 안팎이었다.
  - 이것은 따로 버그 이슈로 다룬다. 위 메모리 표에서는 옛 화면이었던 회를 뺐다.

| 칸 하나 | 0.45.0 | 1 | 531 | 0.53ms | 1.69ms |
| 칸 하나 | 0.45.0 | 2 | 562 | 1.25ms | 2.15ms |
| 칸 하나 | 새 빌드 | 1 | 520 | 1.02ms | 1.89ms |
| 칸 하나 | 새 빌드 | 2 | 572 | 0.64ms | 1.81ms |
| 칸 셋 | 0.45.0 | 1 | 542 | 0.87ms | 2.40ms |

- 가운데값은 같은 빌드끼리도 회마다 두 배 넘게 흔들렸다(0.45.0 칸 하나 0.53~1.25ms). 그래서 판정에 쓰지 않는다.
- p90은 칸 하나에서 비슷했고, 칸 셋에서 2.40~2.57ms가 1.95~2.00ms로 낮았다.

## 판정

- 가설이 맞았다. 셰이더 하나를 건 창의 footprint가 칸 하나 약 11~13MB, 칸 셋 약 15~23MB 줄었고, 화면은 0.45.0과 같았다.
- `gl_FragCoord`를 직접 쓰는 셰이더도 0.45.0과 같은 화면이었다.
- 프레임 시간은 나빠지지 않았다(p90).
- 창 크기 장면 텍스처(칸이 창 전체가 아닐 때)는 그대로 남았다. 없애려면 창 대상 텍스처에 `COPY_SRC`가 필요하다. 셰이더를 쓰지 않는 창에도 닿으므로 이번에는 하지 않았다.

## 재지 않은 것

- 창 대상 텍스처에 `COPY_SRC`를 더해 장면 텍스처를 없애는 길(셈으로는 창 크기 한 장, 약 10.9MB)
- 크기가 다 다른 칸이 여럿인 배치, 칸을 더하거나 닫거나 크기를 바꿀 때
- 셰이더 셋 이상
