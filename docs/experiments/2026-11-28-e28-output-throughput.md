# 실험 E28: PTY 없이 빠른 출력 처리량을 단계별로 재기

- 날짜: 2026-11-28
- 관련 이슈: [#923](https://github.com/dj258255/b-terminal/issues/923), [실험 E14](2026-11-11-e14-gpu-memory-step7.md)(`seq 1 3000000`이 7.1~7.4초)
- 원자료: 주 세션 scratchpad의 `wt-923/` 폴더(`run-*.txt` 측정 출력, `sample-*.txt` `sample` 출력). 저장소에는 넣지 않는다
- 코드 변경은 벤치 예제 `crates/bt-term/examples/throughput.rs` 하나뿐이다. 동작 코드는 바꾸지 않았다

## 가설

> 빠른 출력의 병목은 그리기가 아니라 읽기 쪽(읽기 조각 크기, 엔진 락, VT 파서, 알림 스캐너 `notify.rs` 중 하나)이다. 올린 프레임이 약 430장이라 그리기 시간만으로는 7초가 설명되지 않는다.

## 조건

- 기기: Apple M2 Pro, macOS 26.3.1, `--release`(lto thin, codegen-units 1). **PTY를 열지 않는다**(이 기계는 11-27부터 PTY를 열 수 없다). 같은 바이트를 메모리(또는 파이프)에서 먹인다
- **측정 중 기계 부하가 높았다.** `uptime`의 load average가 9~16, 마지막에는 120까지 올랐다(다른 작업이 같은 기계를 썼다). 그래서 값은 한가한 기계보다 느리게 나왔을 수 있고, 아래 범위가 넓은 줄은 그 탓이다. 가운데 값(5번 중)과 최솟값~최댓값을 적는다
- 엔진 설정은 앱 기본에 맞췄다: 124열 x 40줄, 스크롤백 5만 줄(`scrollback_rows(50MB)`), kitty 키보드 켬. 이벤트 수신기는 아무것도 하지 않는다(`seq`에는 이벤트가 없다)
- 입력 넷(전부 메모리에서 만든다):
  - `seq-crlf`: 정수 1~3000000과 `\r\n`(PTY가 `\n`을 `\r\n`으로 바꾼 꼴), 25.9MB
  - `seq-lf`: 같은 정수에 `\n`만, 22.9MB
  - `seq-bsd`: 이 Mac의 `/usr/bin/seq 1 3000000`이 낸 바이트에 줄마다 `\r`을 붙인 것, 33.7MB. **macOS의 `seq`는 100만부터 `1e+06`·`1.00001e+06` 꼴로 찍어 정수만 찍는 것보다 크다**(`seq 1 3000000 | wc -c`가 30,666,660, 줄은 3,000,001개). 이슈 본문의 "약 20.9MB"는 맞지 않는다
  - `sgr`: `ls --color` 꼴 24MB. 줄마다 기본 16색·256색·트루컬러·굵게/기울임/밑줄/반전 SGR 8개와 한글을 섞은 줄(`\x1b[01;34m…\x1b[0m` 반복)

## 재는 법(재현)

```
cargo run --release -p bt-term --example throughput -- [번수] [조각 크기…]
E28_STAGE=both E28_INPUT=seq-crlf cargo run --release -p bt-term --example throughput -- 12 65536   # 한 단계만(sample용)
E28_PIPE=1 cargo run --release -p bt-term --example throughput -- 5                                   # seq를 파이프로 받아 먹이기
sample <pid> 5 -file out.txt                                                                          # 함수별 시간(macOS)
```

예제는 `cargo test`·CI에서 돌지 않고 빌드만 된다. 단계는 세션 읽기 스레드(`session.rs`의 `bt-pty-read`)가 한 읽기마다 하는 일을 공개 API로 맞춘 것이다.

1. scan: `Scanner::feed_at`만
2. parse: `Processor::advance`와 `Term`만
3. both: `feed_at`, 엔진 `Mutex` 한 번 잡기, 신호 사이마다 `advance`, `take_scroll_log`(읽기 한 번마다)
4. 조각 크기: 512·1024·4096·16384·65536(읽기 스레드 버퍼)·262144
5. pipe: `seq`를 파이프로 받아 64KiB로 읽고 3단계처럼 먹임(읽기 대기와 엔진 시간을 따로 잼)

세션의 읽기 스레드는 여기에 더해 읽을 때마다 `sink(Output)`과 `output_seq` 갱신, `scroll_on_output` 때 락을 한 번 더 잡는 일, 명령 출력 모으기(`capture`)를 한다. 이 몫은 이 벤치에 없다(아래 "재지 못한 것").

## 측정

64KiB 조각(실제 읽기 버퍼 크기), 5번, MB/s는 가운데 값(괄호는 범위). 같은 조건을 두 번 돌린 값을 합쳐 범위를 넓게 적었다.

| 입력 | 1 scan | 2 parse | 3 both | 3 both 걸린 시간 |
|---|---|---|---|---|
| seq-crlf 25.9MB | 663 (613~671) | 39~42 (38~43) | 37~40 (21~40) | 0.65~0.70초 |
| seq-lf 22.9MB | 650~660 (551~663) | 24~31 (19~33) | 29~31 (25~32) | 0.74~0.80초 |
| seq-bsd 33.7MB | 673 (669~679) | 45.6 (41~46) | 35.9 (30~41) | 0.82~0.94초 |
| sgr 24MB | 149 (143~150) | 101~103 (101~104) | 60 (59~61) | 0.40초 |

- 1MB당: scan 1.5ms(seq)·6.7ms(sgr), parse 22~26ms(seq)·9.7ms(sgr), both 25~28ms(seq)·16.5ms(sgr)
- both는 scan과 parse를 더한 값과 맞는다(sgr: 0.16+0.24=0.40초). 락을 한 번 더 잡는 값은 읽기 한 번마다 한 번이라 값에 안 보인다(경합이 없는 락이다)
- `seq`를 파이프로 받아 먹인 5단계: 전체 0.69~0.73초(30.7MB, 42~44MB/s), 그중 읽기 기다림 0.005~0.018초, 스캐너+엔진 0.68~0.70초. `seq`가 쓰는 속도는 병목이 아니다

## 판정

- **읽기 쪽 CPU는 7초의 일부일 뿐이다.** 같은 바이트(25.9~33.7MB)를 스캐너+엔진까지 메모리에서 먹이는 데 0.65~0.94초가 든다(약 30~45MB/s). E14의 7.1~7.4초(같은 `seq`라고 가정하면 약 4.6MB/s)는 이보다 8~11배 길다. 읽기 스레드가 하는 일을 전부 없애도(엔진 시간을 0으로 만들어도) 7.1초에서 아낄 수 있는 것은 많아야 0.9초(약 12%)다. 이 값은 같은 기계·같은 조건이라고 본 추정이다. E14를 재던 때의 부하와 이번 부하가 달랐다
- 가설 "병목은 읽기 쪽 CPU(조각 크기·스캐너·파서·락)"는 **대부분 기각**: 조각 크기는 영향이 없고(512~262144), 락은 경합이 없으면 보이지 않으며, 스캐너는 seq에서 6%(sgr에서 19%)이고, 파서+엔진이 `seq`의 대부분(87~94%)을 쓰지만 절대 시간이 작다
- 병목 후보 순서(재서 확인한 것은 1·2번의 크기뿐이다):
  1. **이 벤치가 못 잰 몫**: 실제 PTY 읽기(읽기 한 번에 오는 바이트 수와 시스템 호출 횟수, tty 쓰는 쪽 `seq`가 막히는 시간), 읽을 때마다 `sink(Output)`으로 UI 스레드를 깨우는 비용, **그리기 스레드가 같은 `inner` 락을 잡고 있는 동안 읽기 스레드가 기다리는 시간**(한 장 그릴 때 스냅샷이 락을 잡는다). 7초 중 약 6초가 여기 있다. 어디인지는 모른다. 가려내려면 PTY가 풀린 뒤 같은 `seq`로 읽기 스레드에 시간 재기를 넣어야 한다(아래 다음에 확인할 것)
  2. 파서+엔진: `seq`에서 `Term::input`(56%)과 `Row::reset`(21%). 줄마다 124칸 새 줄을 지우고 5만 줄 스크롤백 고리를 돌리는 값이다. 3,000,001줄을 0.62초에 처리하니 줄당 약 0.2µs다. 이미 빠르다
  3. 스캐너 CSI 길(SGR이 많은 출력에서 스캐너가 합계의 약 40%, 6.7ms/MB)

## 고칠 방향 후보와 기대 이득(고치지 않았다)

- **A. 스캐너의 CSI 끝에서 모든 CSI마다 하는 일을 줄인다**(`notify.rs`의 `csi_signal`·`csi_inter_signal`). 지금은 SGR(`m`)을 포함한 모든 CSI의 끝 바이트에서 `from_utf8`과 `split(';').collect()`(힙 할당)를 하고 `csi_query::plain`·`visibility`도 부른다. 끝 바이트가 `t`·`h`·`l`·`n`·`y`·`p`처럼 신호가 되는 것이 아니면 곧바로 돌아가고, `m`에서는 아무것도 하지 않게 하면 된다. 기대: 이번 `sample`에서 `from_utf8`+`Vec` 만들기가 sgr 표본의 약 9%라, **SGR이 많은 출력(`ls --color`, 컴파일러 출력)에서 읽기 스레드 시간이 약 5~10% 준다**(추정). `seq` 같은 색 없는 출력에는 효과가 없다. 위험이 작고 시험(`scanner_*` 시험들)이 이미 있다
- **B. 칸 쓰기에서 글자 이어 붙이기 검사**(vendor `alacritty_terminal`의 `Term::input`, `unicode_segmentation` 길). 한글처럼 ASCII가 아닌 글자를 쓸 때마다 `String`을 만들고 묶음을 다시 나눈다(표본의 약 4%). ASCII 앞 글자 뒤의 흔한 경우는 곧바로 돌려보내는 길을 두면 된다. 기대: 한글·CJK 출력에서 몇 %(추정, 이 벤치의 sgr 입력은 한글이 줄 끝에 조금 있을 뿐이라 크기는 모른다)
- **C. `Row::reset`·스크롤백 고리**: `seq`의 21%. 새 줄을 지우는 `Cell` 24바이트 x 124를 한 번에 채우는 길로 바꿀 수 있다. 기대: 엔진 시간의 최대 약 10~15%(추정)지만 전체로는 0.1초 안쪽이라 가치가 낮다
- **D. (가장 큰 것으로 의심) 읽기와 그리기 사이**: 읽기 한 번마다 `sink(Output)`을 보내지 않고 이미 알린 상태면 건너뛰기, 읽기 조각이 작을 때 모아서 한 번에 `advance`, 그리기가 잡은 락 안에서 하는 일 줄이기. 기대: 알 수 없다. 이 실험은 이 몫을 재지 못했다. 실제 PTY로 읽기 스레드의 읽기 대기·락 대기·엔진 시간을 나눠 재기 전에는 고치지 않는 것이 맞다

## 재지 못한 것

- **PTY 읽기와 깨우기 몫**: PTY를 열 수 없어 재지 못했다. 읽기 한 번에 오는 바이트 크기, 읽기 횟수, tty 쓰는 쪽이 막히는 시간
- **엔진 락 경합**: 그리기 스레드가 같은 락을 잡는 몫. 이 벤치는 락을 혼자 쓴다(경합 없음)
- 읽기마다 하는 `sink(Output)`·`output_seq`·`scroll_on_output` 락, `capture`(명령 출력 모으기, 셸 통합이 켜져 있을 때), `sync_graphics`
- 실제 `Listener`(이벤트를 `sink`로 보내는 쪽)와 `Inner`의 나머지(찾기·그래픽). 벤치의 `Term`은 아무것도 하지 않는 수신기를 쓴다
- 이 기계는 부하가 높았다. 한가한 기계에서의 값, 다른 칸 크기(124x40 하나만 잼), 스크롤백 크기에 따른 변화, 알림·그림 같은 다른 OSC·APC가 많은 출력은 재지 않았다
- E14의 7.1~7.4초가 어떤 `seq` 바이트(위에서 보인 BSD `seq`의 30.7MB인지)로 잰 값인지, 같은 부하였는지는 확인하지 않았다

## 덧붙임(#938): 방향 A를 고쳐 다시 잼

방향 A(스캐너 CSI 조기 반환)를 `crates/bt-term/src/notify.rs`에 넣었다. 고친 것: CSI 끝 바이트가 스캐너가 신호를 뽑을 수 있는 것(`c h l n p q r s t y J`, 코드의 `CSI_WATCHED_FINALS`)이 아니면 `from_utf8`·`split(';').collect()`·`csi_query::*`를 부르지 않고 곧바로 `Ground`로 돌아간다. 목록은 코드의 모든 CSI 신호 길에서 끝 바이트를 찾아 만들었다: `csi_signal`(`t h l n`), `csi_query::plain`(`c t h l n`), `private_gt`(`c q`), `visibility`·`kitty_paste`(`h l`), `save_restore`(`s r`), 화면 지우기(`J`), 중간 바이트 길 `csi_inter_signal`(`y p`)·`csi_query::inter`(`p`).

**결과가 같은지**: 시험 `fast_csi_path_matches_full_dispatch`가 끝 바이트 0x40~0x7E 전부 x 앞 표시(`?` `>` `=` `<` `:`, 없음) x 중간 바이트 7가지 x 대표 매개변수 49가지(둘 순서 두 가지)를 거르기를 켠 스캐너와 끈 스캐너(시험 전용 `no_fast_csi`)에 먹여 (자리, 신호) 목록이 같은지 본다. `real_output_shapes_match_the_old_path`는 색 출력·vim 꼴·알림과 질의가 섞인 입력을 조각 1·7·64·전체로 나눠 견주고, `every_final_that_makes_a_signal_is_watched`는 신호를 내는 끝 바이트가 목록과 정확히 같은지 본다. 목록에서 `y`·`J`·`p`·`t`·`q`·`r`을 하나씩 빼면 세 시험이 모두 실패한다.

**잰 값**(release, 64KiB 조각, 한 번에 5번씩 3판 = 15번, 판마다 옛 길과 새 길을 번갈아 돌림, 시작 때 부하 3.3·끝 때 2.9, 같은 기계). 옛 길은 같은 소스에서 거르기만 끈 빌드다.
