# 실험 E10: 기본 길을 GPU로 바꾸면 창을 여는 시간·CPU 시간·메모리가 어떻게 되는가

- 날짜: 2026-11-11(주 세션이 잼)
- 관련 이슈: [#368](https://github.com/dj258255/b-terminal/issues/368), [실험 E9](2026-11-11-e9-frame-pacing.md), [ADR-039](../decisions.md)
- 원자료: 주 세션 scratchpad의 `e10/` 폴더(회마다 로그). 저장소에는 넣지 않는다

## 가설

> E7~E9는 프레임 하나의 시간만 쟀다. GPU 길은 창마다 wgpu Instance·어댑터·장치·아틀라스를 따로 연다. 그래서 (1) 창을 띄워 글이 보이기까지가 늘고, (2) 메모리(RSS)가 는다. 대신 (3) 같은 장면을 그리는 동안 프로세스가 쓰는 CPU 시간은 준다.

## 이 실험이 정할 것

> 이슈 #368의 기준을 그대로 쓴다: **창을 여는 시간이 사람이 느낄 만큼(100ms 넘게) 늘거나 RSS가 두 배를 넘으면 기본을 바꾸지 않고 원인부터 연다. 아니면 바꾼다.**

## 조건

- 기기: Apple M2 Pro, macOS 26, 내장 화면(120Hz), `--release`, 창 1000×680pt(2000×1360px)
- 격리: `HOME`을 빈 폴더로, `TMPDIR`을 짧은 경로로, 설정 파일은 E9와 같다
- 바꾼 변수: 그리기 길 하나(`BT_GPU=0` = CPU / 환경 변수 없음 = 새 기본, macOS라 GPU). 두 조건을 번갈아 다섯 번씩, 회마다 앱을 새로 띄운다
- `RUST_LOG=info`. 프레임마다 찍는 debug 로그가 CPU 시간에 섞이지 않게 한다
- 빌드는 이 PR의 것이다. 로그 두 줄을 더했다(아래).

## 지표 정의

- **첫 프레임**: 앱이 남기는 `첫 프레임(GPU|CPU): 창을 만든 뒤 …ms, 앱을 띄운 뒤 …ms, …`의 "앱을 띄운 뒤" 값. `main` 맨 앞에서 잰 때부터 창에 처음 올린 때까지다.
- **창이 보임**: macOS가 창이 보이게 됐다고 처음 알린 때(`WindowEvent::Occluded(false)`). 첫 프레임보다 먼저 오면 첫 프레임 줄에 `창이 보인 뒤 …ms`로, 나중에 오면 `창이 보임: 첫 프레임을 올리고 …ms 뒤` 줄로 남는다.
- **글이 보인 때**: 위 둘 가운데 늦은 쪽. 사람이 창에서 글을 처음 볼 수 있는 때로 본다. 알림 시각이 실제로 화면에 나타난 시각과 얼마나 다른지는 재지 않았다.
- **CPU 시간**: 장면 C(0.2초마다 37줄 전체, 60번)를 보내기 직전과 13초 뒤에 `ps -o time=`을 읽은 차이. 해상도는 0.01초다.
- **RSS**: 같은 두 때의 `ps -o rss=`.

## 잴 명령

1. 빌드: `cargo build --release -p bt-app -p bt-ctl`
2. 한 회: `RUST_LOG=info HOME=<빈 폴더> TMPDIR=<짧은 폴더> [BT_GPU=0] ./target/release/b-terminal --config-file <E9 설정> 2> <로그>`. 제어 소켓이 생기면 1.5초 기다린다. `ps -o time=,rss= -p <pid>`를 읽고 `btctl send`로 장면 C(E7 문서의 명령)를 보낸다. 13초 뒤 `ps`를 다시 읽고 앱을 끈다.
3. 로그에서 `그리기 길:`, `첫 프레임`, `창이 보임` 줄을 읽는다.

## 결과

주 세션이 쟀다. 다섯 회의 범위이고 괄호 안은 중앙값이다.

| | CPU(`BT_GPU=0`) | GPU(기본) |
|---|---|---|
| 첫 프레임(앱을 띄운 뒤) | 187.0~229.8ms (221.9) | 273.6~319.0ms (308.0) |
| 창이 보임(앱을 띄운 뒤) | 261.0~290.3ms (274.6) | 251.5~289.7ms (256.4) |
| **글이 보인 때** | 261.0~290.3ms (274.6) | 273.6~319.0ms (308.0) |
| 창이 보인 뒤 첫 프레임까지 | −74.0~−48.5ms(보이기 전에 올림) | +18.3~+60.1ms (+23.3) |
| 장면 C의 CPU 시간 | 0.34~0.37초 | 0.19~0.21초 |
| RSS, 장면 전 | 140~141MB | 189~190MB |
| RSS, 장면 뒤 | 153~158MB | 171~177MB |

- GPU 장치를 여는 데(`그리기 길: GPU(장치 열기 …ms)`) 위 다섯 회는 6.2~6.6ms, debug 로그로 띄운 세 회는 10.5~11.3ms가 들었다.
- 화면 비교: 이 빌드를 환경 변수 없이(GPU)와 `BT_GPU=0`(CPU)으로 띄워 창을 찍었다. 기본·진행 막대·합자(JetBrains Mono)·투명 창(불투명도 0.8, 흐림)은 다른 픽셀 0개였다. 분할은 흐린 옆 칸에서만 채널 1 차이(11,319픽셀)가 났다. `window-colorspace = srgb`면 `GPU 길을 쓰지 못해 CPU 길로 그린다: window-colorspace = srgb`를 남기고 CPU로 그렸다.

### 읽은 것

- **글이 보인 때는 약 33ms 늦다**(중앙값 274.6 → 308.0ms). 기준 100ms보다 작다.
  - CPU 길은 창이 보이기 49~74ms 전에 첫 프레임을 올려 둔다. 창이 보이는 순간 글이 있다.
  - GPU 길은 창이 보이기 전에는 그림판을 얻지 못한다(wgpu가 `Occluded`를 돌려준다, ADR-038). 그래서 보인다는 알림을 받은 뒤 다시 그린다. 그동안 창에는 그림이 없다. 이 시간이 18~60ms(중앙값 23ms)다.
- **빈 창 시간의 내역**(debug 로그 세 회)
  - 첫 보이는 프레임 자체는 13.9~14.6ms였다. 그중 층 21,760,000바이트 올리기가 9.7~9.9ms다.
  - 나머지 7~23ms는 보인다는 알림을 받은 뒤 다시 그리기가 불리기까지다.
- **CPU 시간은 약 절반이다.** 같은 장면을 그리는 동안 프로세스가 쓴 시간이 0.34~0.37초에서 0.19~0.21초가 됐다.
- **RSS는 장면 전 약 49MB, 장면 뒤 약 19MB 크다.** 두 배와는 거리가 멀다. GPU 길은 장면 뒤에 오히려 RSS가 줄었다(189 → 177MB). 왜 그런지는 보지 않았다.

### 해 보고 버린 것: 보이기 전에 층을 올려 두기

빈 창 시간을 줄이려고, 한 번도 올리지 못한 창은 가려졌어도 층을 올려 두게 해 봤다(그러면 보이는 첫 프레임은 바뀐 곳만 올린다). 다섯 쌍을 다시 쟀다.

- 첫 보이는 프레임은 14ms에서 4.2~5.6ms가 됐다(층 0바이트).
- 그러나 빈 창 시간은 12.7~26.0ms(중앙값 24.3)로 거의 그대로였다.
- 창이 보이는 때는 276.2~295.8ms(중앙값 293.4)로 오히려 늦었다. 보이기 전 첫 프레임이 메인 스레드에서 층 올리기에 약 15ms를 쓰기 때문으로 짐작한다.
- 글이 보인 때는 288.9~321.2ms(중앙값 317.7)였다.
- 나아지지 않아 넣지 않았다. 빈 창 시간의 대부분은 층 올리기가 아니라, 보인다는 알림에서 다시 그리기까지의 지연이다.

## 판정

- 기준(100ms 넘게 늘거나 RSS 두 배)에 걸리지 않는다. 기본 길을 바꾼다(macOS만, ADR-039).
- 대가: 창을 띄울 때 글이 약 33ms 늦게 보이고, 그동안 창에 그림이 없다(약 23ms). 메모리는 약 20~50MB 더 쓴다.
- 얻는 것: 그리는 동안 CPU 시간이 약 절반이다. 프레임 하나의 메인 스레드 시간도 E9처럼 짧다.
- 남은 일: 보인다는 알림에서 다시 그리기까지의 지연(7~23ms)을 줄이는 방법(알림을 받은 자리에서 바로 그리기 등)은 시험하지 않았다. → 실험 E12에서 알림을 받은 자리에서 바로 그리게 해 이 몫을 없앴다.

## 한계

- 한 기기(Apple M2 Pro 내장 화면)의 값이다. 외부 화면, 다른 GPU, Intel Mac은 재지 않았다.
- 창 하나만 쟀다. 창을 여럿 열 때 창마다 장치를 따로 여는 비용(메모리)이 어떻게 쌓이는지는 재지 않았다.
- "창이 보임"은 macOS 알림을 받은 때다. 화면에 실제로 그려진 때는 재지 않았다.
