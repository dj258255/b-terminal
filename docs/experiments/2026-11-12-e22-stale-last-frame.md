# 실험 E22: GPU 길에서 마지막 프레임이 화면에 붙지 않는 일

- 날짜: 2026-11-12(주 세션이 잼)
- 관련 이슈: [#447](https://github.com/dj258255/b-terminal/issues/447), 추적 [#444](https://github.com/dj258255/b-terminal/issues/444)
- 원자료: 주 세션 scratchpad의 `e21/`·`e22/` 폴더(측정 스크립트, 화면, 로그). 저장소에는 넣지 않는다

## 찾은 경위

실험 E21에서 셰이더 둘을 건 칸 하나 창이 새 빌드에서만 세 회 중 두 회 옛 화면이었다. 같은 장면을 더 돌리자 0.45.0에서도, 셰이더가 없어도 같은 일이 났다.

## 가설

> 앱은 마지막 프레임을 올리는데, 그림판이 둘뿐이라 화면이 한 장을 오래 쥔 때 올린 프레임이 화면에 붙지 않는다. 그림판을 한 장 더 허락하면(앱의 줄 깊이는 그대로) 사라진다.

## 조건

- Apple M2 Pro 내장 120Hz, macOS 26, `--release`, 저전력 모드 켜짐, 창 1000×680pt(2000×1360px)
- 격리 `HOME`·`TMPDIR`, `window-save-state = never`, `shell-integration = none`, `cursor-style-blink = false`, 셰이더 없음
- 회마다 새로 띄운다. 1.5초 뒤 `btctl send --enter "clear; echo pa''ne"`, `btctl wait -- pane`(종료 코드 0으로 끝남), 3초 뒤에 찍는다
- 판정
  - 둘째 줄 가운데(x 100~600, y 95~130)에 밝은 픽셀이 있으면 새 화면(`pane` 뒤 프롬프트)이다.
  - 없으면 옛 화면(`clear`를 친 줄과 그 아래 커서)이다.

### 로그(계측 빌드, `RUST_LOG=b_terminal=debug,bt_gpu=debug`)

- 옛 화면 회와 새 화면 회의 로그는 꼴이 같았다.
  - `surface 설정`은 처음 한 번
  - 첫 얻기는 `Occluded`
  - 가림이 풀린 뒤 `올림 #1`(통째, 층 10,880,000바이트)
  - 셸 출력에 `올림 #2`
  - 미룸 4~5번 뒤 깨우기가 1.5~2ms 늦게 발화해 `올림 #3`
- 얻기는 모두 `Success`였다. Suboptimal·크기 바뀜·층 텍스처 다시 잡기는 없었다.
- 사람이 보는 화면 합성본(`screencapture -R`, 창 자리)도 창 찍기(`-l`)와 같이 옛 화면이었다(다섯 회 중 두 회, 둘 다 일치).

| 장면 | main | 고친 빌드 |
|---|---|---|
| 셰이더 없음, 옛 화면 | 10회 중 6회 | 10회 중 0회 |
| 셰이더 없음, footprint | 새 화면 85.6~86.2MB(넷), 옛 화면 95.9~96.8MB(여섯) | 85.8~86.3MB(여섯), 96.3~96.9MB(넷) |
| 셰이더 하나 멈춤, 칸 하나 | 110.8MB(새), 120.8MB(옛) | 120.8~120.9MB |
| 셰이더 하나 멈춤, 칸 셋 | 142.4~144.5MB | 153.2~154.4MB |
| 셰이더 하나 `always`, 칸 하나 | 127.4~128.1MB | 138.8~139.3MB |

- 셰이더를 건 창은 고친 빌드에서 열 회 모두 셋째 그림판만큼(약 10MB) 컸다. 셰이더 패스로 GPU 일이 길어 화면이 쥔 장과 그리는 장 말고 한 장이 더 필요해지는 것으로 본다(확인 안 함).
- 칸 셋 셰이더 화면은 고친 빌드와 main이 두 회씩 다른 픽셀 0이었다.

### 입력 지연(앱이 재는 "입력 → 화면", main 바이너리, 지연 1·2를 번갈아 두 회씩, 회마다 41~42글자)

| 장면 | 지연 1 | 지연 2 |
|---|---|---|
| 한가할 때(`cat`) | 가운데 1.6ms, p90 1.7ms | 가운데 1.6ms, p90 1.8ms |
| 옆 칸이 `seq`를 계속 찍을 때 | 가운데 7.9ms, p90 15.8ms | 가운데 7.1ms, p90 15.5ms |

이 값은 앱이 올릴 때까지다. 올린 뒤 화면에 보이기까지의 줄 대기는 재지 못한다.

## 판정

- 가설이 맞았다. 앱은 마지막 프레임을 올렸지만 화면에는 그 앞 프레임이 남았다.
  - 옛 화면 회는 늘 그림판 한 장(10.88MB)만큼 footprint가 컸다.
  - 그림판이 둘로 묶였어도 화면이 한 장을 오래 쥔 때 한 장이 더 생긴 것으로 본다. 그런데도 그 프레임은 붙지 않았다. 왜 붙지 않는지(합성기·`CAMetalLayer` 안쪽)는 확인하지 못했다.
- 앱의 줄 깊이는 1로 두고 surface에만 그림판 한 장 여유(`desired_maximum_frame_latency` 2)를 주면 사라졌다.
  - 셰이더 없는 창의 footprint는 화면이 셋째를 쓴 회만 늘었고, 그 값(96MB)은 지금 옛 화면 회가 이미 내던 것과 같았다.
  - 셰이더를 건 창은 늘 셋째를 써서 약 10MB 늘었다. 실험 E21에서 텍스처 나눠 쓰기로 아낀 몫(칸 하나 약 11MB)의 대부분이 돌아간다. 맞게 보이는 것을 먼저 두고 받아들였다.
- 0.36에서 메모리를 줄이려고 지연을 2에서 1로 내린 뒤부터로 짐작한다. 0.35 바이너리로는 재지 않았다.

## 재지 않은 것

- `window-vsync = false`(Immediate)에서 남는 옛 화면. 여유 그림판으로도 사라지지 않았다.
- 외부 화면, 60Hz 화면, 저전력 모드를 끈 상태, 오래 쓴 창(띄운 직후 1초 안팎만 봄)
- 0.35 이전
- 올린 뒤 화면에 보이기까지의 지연
