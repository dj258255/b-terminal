# 실험 E23: `window-vsync = false`에서 마지막 프레임이 화면에 붙지 않는 일

- 날짜: 2026-11-12(주 세션이 잼)
- 관련 이슈: [#451](https://github.com/dj258255/b-terminal/issues/451), 추적 [#450](https://github.com/dj258255/b-terminal/issues/450), 앞 실험 [E22](2026-11-12-e22-stale-last-frame.md)
- 원자료: 주 세션 scratchpad의 `e21/`·`e23/` 폴더(측정 스크립트, 화면, 로그). 저장소에는 넣지 않는다
- 실험 빌드: 브랜치 `exp/vsync-stale`(병합하지 않음). 환경 변수 스위치로 후보를 켜고 끈다. 몇은 주 세션이 측정용으로만 넣었다

## 찾은 경위

E22에서 그림판 여유 한 장으로 기본 설정의 옛 화면은 사라졌지만, `window-vsync = false`(Immediate)에서는 네 회 중 세 회 남았다.

## 조건

E22와 같다.
- Apple M2 Pro 내장 120Hz, macOS 26, `--release`, 저전력 모드 켜짐, 창 2000×1360px, 셰이더 없음
- 회마다 새로 띄운다. `clear; echo pa''ne`를 보내고 `btctl wait -- pane`이 끝난 뒤 3초 뒤에 찍는다
- 판정
  - 둘째 줄 가운데에 밝은 픽셀이 있으면 새 화면이다.
  - 없으면 옛 화면(`clear`를 친 줄과 그 아래 커서)이다.

## 측정 사고

- 처음에는 세 묶음(스위치 다섯, 고친 빌드와 0.46.0, 셋을 번갈아 잰 것)의 회별 판정을 macOS `awk`로 모았다.
- 그 `awk`는 한글 판정 글자 '새'와 '옛'을 같은 값으로 견주어 모든 회를 옛 화면으로 셌다. 로케일 정렬로 견주는 탓으로 보며, 확인은 하지 않았다.
- 그래서 한동안 "다시 올리기는 효과가 없다", "고친 빌드도 옛 화면이다"로 잘못 읽었다.
- 아래 표는 모두 저장한 화면을 파이썬으로 다시 판정한 값이다.

## 결과

### 1. 앱이 넘긴 화면 내용은 맞다

- GPU 프레임마다 그리기에 넘긴 `view`와 엔진(`Session`)의 맨 위 두 줄을 같이 남겼다(debug 로그 `b_terminal::e23`).
- 옛 화면 회에서도 마지막 프레임의 `view`와 엔진은 같았다. 둘 다 `pane`과 그 뒤 프롬프트였다.
- 앱은 그 프레임을 "바뀐 줄 2줄"로 그려 `Presented`로 올렸다. 그런데 화면은 그 두세 프레임 앞 내용이었다.

### 2. 빈도

| 빌드·설정 | 옛 화면 | footprint |
|---|---|---|
| 0.46.0, `false` | 16회 중 14회 | 옛 107.4~121.6MB, 새 96.7~96.8MB |
| 0.46.0, `true` | 6회 중 0회 | 85.7~96.5MB |
| 실험 빌드, Immediate + 미룸 끔(지금 `false`와 같음) | 19회 중 17회 | 옛 107.6~120.8MB, 새 96.8~96.9MB |
| 실험 빌드, `Fifo` + 미룸 끔(측정용) | 6회 중 3회 | 옛 106.9~107.4MB, 새 96.4~98.6MB |
| 실험 빌드, `Fifo` + 미룸 켬(`true`와 같음) | 6회 중 0회 | 85.5~96.2MB |
| **실험 빌드, Immediate + 미룸 켬(측정용)** | **11회 중 0회** | 86.4~98.4MB |
| 마지막 프레임 16ms 뒤 같은 내용을 1번 더(`BT_E23_REPRESENT=1`) | 6회 중 0회 | 96.5~97.4MB |
| 같은 것 3번(`BT_E23_REPRESENT=3`) | 6회 중 0회 | 96.8~99.6MB |
| 다시 올릴 때만 `Fifo`(`BT_E23_FIFO_IDLE=1`) | 6회 중 0회 | 96.6~99.1MB |
| 올린 뒤 GPU가 마칠 때까지 기다림(`BT_E23_POLL_WAIT=1`) | 6회 중 5회 | 옛 107.1~108.3MB, 새 96.7MB |
| 프레임마다 통째로 그림(`BT_E23_FULL=1`) | 4회 중 0회 | 97.1~99.1MB |
| 바뀐 것이 없는 프레임도 올림(측정용) | 4회 중 0회 | 97.4~99.1MB |

- 옛 화면 회는 하나도 빠짐없이 footprint가 107MB 이상이었다. 새 화면 회는 86~101MB였다. 그림판이 한두 장 더 잡혀 있는 것으로 본다.
- 옛 화면 회는 출력 뒤 프레임을 1ms 안팎 간격으로 몰아 올렸고, 그림판 얻기에서 기다린 적이 없었다(0.2~0.8ms).
- 화면이 맞은 경우는 둘이다.
  - 미룸을 켜 몰아 올리지 않은 경우
  - 마지막 프레임 뒤에 프레임을 더 올린 경우: 다시 올리기, 통째 그리기, 바뀐 것 없는 프레임 올리기. 통째 그리기와 빈 프레임 올리기는 그림판 얻기에서 13~23ms를 기다렸다.
- `Fifo`여도 미룸을 끄면 났다. 원인은 Immediate 자체가 아니라, 화면 주기보다 빨리 그림판을 몰아 올리는 것으로 본다. 합성기 안에서 왜 붙지 않는지는 확인하지 못했다.
- 명령을 두 번 보내고 두 번째 뒤에 찍으면 지금 빌드도 세 회 모두 새 화면이었다. 띄운 직후 첫 출력에서 잘 난다. 이유는 모른다.

## 판정

`window-vsync = false`에서도 프레임 미룸을 켠다. 올리기 방식은 `Immediate` 그대로 둔다(ADR-045).

## 고친 빌드

| | 고친 빌드 | 0.46.0 |
|---|---|---|
| `false` 옛 화면(번갈아 열 회, 따로 다섯 회) | 15회 중 0회, 96.2~97.8MB | 10회 중 9회 |

로그에 `화면 갱신 맞춤 끔(Immediate)`이 찍히고, 출력 끝에서 한 번 미룬 뒤 마지막 프레임을 올렸다.

## 대가: 빠른 출력

방법은 E16과 같다(`seq 1 300000`을 보내고 끝날 때까지의 시간, 올린 프레임의 그림판 얻기 시간 합). 네 가지를 번갈아 세 회씩 쟀다. 1분 부하는 3~4였다.

| 빌드·설정 | 걸린 시간 | 얻기 합 | 1ms 넘는 얻기 |
|---|---|---|---|
| 0.46.0 `true` | 0.57~0.58초 | 11~16ms | 4~5 / 36~38 |
| 0.46.0 `false` | 0.39~0.40초 | 336~342ms | 30~33 / 37~46 |
| 고친 빌드 `true` | 0.56~0.57초 | 12~15ms | 3~5 / 37~38 |
| 고친 빌드 `false` | 0.56~0.58초 | 10~15ms | 3 / 29~47 |

- `false`의 빠른 출력 이득(약 30%)은 없어졌다. E16의 "미룸 켬" 실험 빌드(0.56~0.58초)와 같다.
- 출력 중 메인 스레드가 그림판을 기다리며 막히던 시간도 없어졌다.
- `false`에 남은 차이는 올릴 때 화면 갱신을 기다리지 않는다는 것(찢어질 수 있음)뿐이다. 그것이 화면에 보이기까지의 지연을 줄이는지는 재지 않았다.

## 택하지 않은 것

- **마지막 프레임 뒤 다시 올리기(`REPRESENT`)**
  - 12회 중 0회로 옛 화면을 없앴고, 미룸을 끈 채라 빠른 출력 이득도 남는다.
  - 그러나 왜 듣는지 모른다.
  - 출력 중 프레임마다 메인 스레드가 약 15ms씩 막히는 일도 그대로다.
  - ADR-044에서 같은 까닭으로 택하지 않았다.

## 재지 않은 것

- 외부 화면, 60Hz 화면, 저전력 모드를 끈 상태, 오래 쓴 창
- 합성기·`CAMetalLayer` 안에서 마지막 올림이 붙지 않는 까닭(`unsafe` 없이는 들여다볼 수 없음)
- 키를 친 뒤 화면에 보이기까지의 지연(`true`·`false` 모두)
