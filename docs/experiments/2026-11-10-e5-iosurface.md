# 실험 E5: 프레임을 IOSurface로 올리면 올리기까지가 줄어드는가

- 날짜: 2026-11-10(만든 날. 잰 날은 결과 칸에 적는다)
- 관련 이슈: [#346](https://github.com/dj258255/b-terminal/issues/346), [실험 E3](2026-11-06-e3-present.md), [실험 E4](2026-11-06-e4-buffer-reuse.md), [ADR-034](../decisions.md)
- 커밋: feature/iosurface-present 브랜치(이 실험을 넣은 PR)
- 원자료: 아래 "결과"의 출력이 전부다

## 가설

> 실험 E4 뒤 큰 창에서 바뀐 줄 하나짜리 프레임의 올리기까지는 약 3~5ms이고 대부분이 옮기기(프레임 → softbuffer 버퍼 복사)였다. 프레임을 IOSurface에 곧장 한 번만 복사해 레이어 `contents`로 넣으면(Ghostty와 같은 길) 올리기까지의 중앙값이 줄어든다.

## 이 실험이 정할 것

> 같은 조건 다섯 쌍에서 올리기까지 중앙값이 줄면 IOSurface를 기본으로 둔다(지금 코드의 기본). 줄지 않으면 결과를 남기고 기본을 CGImage(`BT_E5_CGIMAGE`가 있을 때의 길)로 되돌린다.

## 조건

E3·E4와 같게 한다.

- 기기: Apple Silicon Mac(arm64), macOS 26.3.1, `--release`, 내장 화면, 창 1000×680pt(2000×1360px), `window-colorspace` 기본
- 내용: 화면을 채운 뒤 한 줄만 0.25초마다 바꾼다(한 번 띄울 때 약 58프레임). 바뀐 줄 하나를 만드는 방법은 아래 "잴 명령"
- 바꾼 변수: 올리기 길 하나(IOSurface / CGImage). 두 조건을 **번갈아 다섯 번씩** 띄운다(E4와 같다). 같은 시각, 같은 부하에서 쌍으로 견주려는 것이다
- 격리: 사용자 설정을 건드리지 않게 `HOME`을 빈 폴더로, `TMPDIR`을 짧은 경로로 바꾼다(제어 소켓 경로 길이 때문)

## 지표 정의

E3·E4와 같다. 앱이 `RUST_LOG=debug`일 때 프레임마다 찍는 한 줄에서 읽는다.

```
다시 그리기: 바뀐 줄 1줄 그리기 …ms, 올리기까지 …ms (크기 … 버퍼 … 옮기기 … present …)
```

- 올리기까지: 프레임 올리기 시작부터 끝까지(크기 + 버퍼 + 옮기기 + present). 프레임마다의 중앙값을 한 회의 값으로 쓰고, 다섯 회의 중앙값을 비교한다.
- IOSurface 길에서는 프레임을 IOSurface에 곧장 복사하므로 `버퍼`와 `옮기기`는 0에 가깝고 복사 시간이 `present` 안에 든다. 그래서 **세 칸이 아니라 "올리기까지"만 길 사이에서 견준다**.

## 잴 명령

주 세션이 창을 띄워 잰다. 이 문서를 쓴 에이전트는 창을 띄우지 않았다.

1. 빌드: `cargo build --release -p bt-app`
2. IOSurface 길(기본): `RUST_LOG=debug HOME=<빈 폴더> TMPDIR=/tmp/bt ./target/release/b-terminal 2> e5-iosurface-<회>.log`
3. CGImage 길: 위와 같고 환경 변수만 더한다: `BT_E5_CGIMAGE=1 RUST_LOG=debug …`
4. 창 크기를 1000×680pt(2000×1360px)로 맞춘다.
5. 바뀐 줄 하나를 만든다. 창 안의 셸에서 화면을 채우고 첫 줄만 갱신한다:
   ```
   clear; seq 1 80
   while :; do printf '\033[1;1H%s' "$(date +%T)"; sleep 0.25; done
   ```
   (`seq`는 화면을 채우는 용도이고, 이후 `\033[1;1H`로 맨 윗줄만 덮는다. 12초쯤 두었다가 닫는다.)
6. 중앙값: 로그에서 `바뀐 줄 1줄`인 프레임의 "올리기까지"만 뽑아 가운데 값을 낸다.
   ```
   grep '바뀐 줄 1줄' e5-<길>-<회>.log | sed -E 's/.*올리기까지 ([0-9.]+)ms.*/\1/' | sort -n | awk '{a[NR]=$1} END {print a[int((NR+1)/2)]}'
   ```
7. 두 길을 번갈아 5회씩 하고 쌍마다 표에 옮긴다.
8. 확인할 것(재기와 같은 실행에서 눈으로): 아래 "실제 창에서 볼 것".

## 실제 창에서 볼 것(색·투명·크기)

가설과 별개로, 이전과 같게 보여야 하는 것들이다. 같은 설정으로 `BT_E5_CGIMAGE=1`과 기본의 화면을 나란히 본다.

- 색: 기본(`window-colorspace` 없음)과 `window-colorspace = srgb`. 바탕·글자색이 두 길에서 같게 보이는지(특히 `srgb`는 이전 "기기 RGB"에서 이름 있는 sRGB로 바뀌었다).
- 불투명 창이 비쳐 보이지 않는지(알파를 `0xff`로 채운다).
- 투명: `background-opacity = 0.8`, 그리고 `background-blur = true`(곱한 알파가 그대로 보이는지).
- 창 크기를 끌어 바꿀 때 깜빡임·옛 크기 그림이 남지 않는지(묶음을 비운다), Retina 화면에서 흐리거나 반쪽만 차지하지 않는지.
- 찢어짐: 빠르게 출력(`yes | head -c 20000000`)할 때 화면이 반쯤 새것·반쯤 옛것으로 보이지 않는지.
- 창을 다른 화면으로 옮길 때(#97) 색이 바뀌는지(외부 모니터가 있을 때만).

## 창 없이 잰 값(에이전트, 한 번 잰 값)

- 진짜 IOSurface(2000×1360, 32BGRA)를 만들어 잠그고 `copy_frame`(불투명, 알파 채움)으로 프레임을 복사한 뒤 푸는 데 걸린 시간을 `--release` 단위 시험에서 30번 재 **중앙값 0.60ms**(최소 0.53, 최대 1.39ms). 같은 IOSurface에 되풀이 썼으므로 쪽이 이미 달려 있고 Core Animation이 쥔 적이 없는 경우다. 실제 창의 값은 아니다. 한 번 잰 값이다.
- 이 기기에서 시스템이 잡은 `bytesPerRow`는 폭 2000px에서 8064바이트(폭×4 = 8000에 64바이트 덧칸), 폭 37px에서 256바이트(폭×4 = 148)였다. 줄 간격을 지켜 줄마다 복사해야 하는 경우가 실제로 있다.
- 창 없이는 Core Animation이 IOSurface를 쥐는 시간, 합성, 쪽 부재를 잴 수 없다.

## 배제한 원인과 남은 가능성

- 주 세션이 잰 뒤 적는다. 미리 적어 둘 위험은 다음과 같다. IOSurface를 쓰는 동안 Core Animation이 같은 것을 읽으면 찢어질 수 있어 `IOSurfaceIsInUse`가 아닌 것만 쓰고 지금 `contents`인 것은 쓰지 않는다. 이 검사가 충분한지는 실제 창에서 본 것이 없다.
- IOSurface에 색 공간을 붙이면 Core Animation의 색 맞춤 변환을 피하는지는 재야 안다(E3에서 기기 RGB는 프레임마다 약 14ms였고 화면 색 공간 객체는 약 0.1ms였다).
