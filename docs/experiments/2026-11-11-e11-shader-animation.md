# 실험 E11: 사용자 셰이더가 움직이는 동안 CPU와 메인 스레드를 얼마나 쓰는가

- 날짜: 2026-11-11(주 세션이 잼)
- 관련 이슈: [#376](https://github.com/dj258255/b-terminal/issues/376), [ADR-040](../decisions.md), [ADR-041](../decisions.md), [실험 E9](2026-11-11-e9-frame-pacing.md)
- 원자료: 주 세션 scratchpad의 `e11/` 폴더(회마다 로그). 저장소에는 넣지 않는다

## 가설

> 셰이더가 움직이면(Ghostty와 같이 8ms마다 다시 그림) 가만히 둔 창도 프레임을 계속 그린다. 프레임 하나는 E9처럼 짧으니(바뀐 줄 0줄, 층 올리기 없음) CPU는 조금 쓰고 메인 스레드는 막히지 않는다.

## 이 실험이 정할 것

> 셰이더를 걸고 가만히 둔 창이 메인 스레드를 오래 막거나(10초에 1초 넘게) CPU를 코어 하나의 10% 넘게 쓰면, 애니메이션 간격이나 프레임 미루기를 다시 정한다. 아니면 그대로 둔다.

## 조건

- 기기: Apple M2 Pro, macOS 26, 내장 화면(120Hz), `--release`, 창 1000×680pt(2000×1360px), GPU 길(기본)
- 격리: `HOME`을 빈 폴더로, `TMPDIR`을 짧은 경로로. 설정은 `window-save-state = never`, `shell-integration = none`에 아래 셰이더만 더함
- 바꾼 변수: 설정 넷
  - 셰이더 없음
  - 항등 셰이더(`fragColor = texture(iChannel0, fragCoord / iResolution.xy)`)
  - Ghostty `test_shadertoy_crt.glsl`
  - crt에 `custom-shader-animation = false`
- 넷을 번갈아 세 번씩 돌리고, 회마다 앱을 새로 띄운다
- 한 회: 띄우고 1.5초 → `clear; seq 1 20` → 1.5초 → `ps -o time=,rss=` → 10초 가만히 → `ps` → 끈다
- CPU 시간은 `RUST_LOG=info`로 잰다. 프레임 수와 시간은 `RUST_LOG=debug`로 한 번 더 띄워 GPU 프레임 로그(`다시 그리기:` 줄)에서 센다. 로그 시각이 초 단위라 10초 구간의 프레임 수는 ±1초쯤 어긋날 수 있다.

## 결과

### 처음 이은 빌드(미루기 판단은 0.32 그대로)

| 설정 | 10초 CPU 시간 | 10초 프레임 | 프레임 "올리기까지" 중앙값 | 얻기 1ms 넘는 프레임 | 얻기에서 기다린 합 |
|---|---|---|---|---|---|
| 셰이더 없음 | 0.00~0.01초 | 0 | - | - | - |
| 항등 | 0.50~0.52초 | 576 | 16.42ms | 576 | 9.28초 |
| crt | 0.51초 | 578 | 16.38ms | 578 | 9.30초 |
| crt, 애니메이션 끔 | 0.01초 | 0 | - | - | - |

- 그림판 얻기가 프레임마다 12.1~19.4ms(가운데 90%는 15.4~16.6ms) 걸렸다. 10초 가운데 9.3초 동안 메인 스레드가 얻기에서 기다렸다. 그동안 키 입력 처리가 밀린다.
- 프레임 미루기(ADR-038)도 돌았다(미룬 프레임이 계속 늘었다). 그런데 "화면이 8.3ms마다 한 장을 가져간다"는 짐작으로 통과시킨 프레임이 남은 시간만큼 막혔다. 실제로는 약 16.6ms마다 한 장씩 빠졌다(초당 약 58장).
- 기준(10초에 1초 넘게 막힘)에 걸렸다. 미루기 판단을 고쳤다(ADR-041 결정 5): 얻기에서 막힌 프레임의 간격을 배운다.

### 미루기 판단을 고친 빌드

| 설정 | 10초 CPU 시간 | 10초 프레임 | 프레임 "올리기까지" 중앙값 | 얻기 1ms 넘는 프레임 | 얻기에서 기다린 합 |
|---|---|---|---|---|---|
| 셰이더 없음 | 0.01초 | (재지 않음) | - | - | - |
| 항등 | 0.52~0.53초 | 584 | 0.30ms | 70 | 0.18초 |
| crt | 0.52~0.54초 | 586 | 0.30ms | 82 | 0.20초 |
| crt, 애니메이션 끔 | 0.01초 | (재지 않음) | - | - | - |

- 프레임 수는 거의 같고(초당 약 58장), 얻기에서 기다린 시간이 9.3초에서 0.2초로 줄었다.
- 아직 1ms 넘게 막히는 프레임이 12~14% 남는다. 배운 간격을 1%씩 줄여 가다 다시 막히면 다시 배우기 때문이다.
- CPU 시간은 고치기 전과 같다(코어 하나의 약 5%).
- RSS는 넷 모두 172~176MB로, 셰이더 유무에 따른 차이를 가를 수 없었다.

### 미루기 판단을 바꾼 것이 다른 장면을 나쁘게 하지 않는가

- 장면 C(E10과 같은 명령, 0.2초마다 37줄 전체, 셰이더 없음), 고친 빌드로 세 회:
  - 올린 프레임 122~123
  - 얻기 1ms 넘는 프레임은 회마다 1(처음 보이는 프레임)
  - 바뀐 줄 프레임 중앙값 0.67~0.73ms
  - 10ms 넘는 프레임 회마다 1
- E10 때(0.32 빌드) 같은 장면을 debug로 잰 세 회:
  - 올린 프레임 123~124
  - 얻기 1ms 넘는 프레임 1
  - 바뀐 줄 중앙값 0.67~0.70ms
  - 10ms 넘는 프레임 1
- 다른 때에 잰 값이라 번갈아 잰 쌍은 아니다.
- 셰이더 없이 `seq 1 300000`을 쏟을 때는 23프레임 가운데 한 프레임이 얻기에서 15.2ms 막혔고, 그 뒤로 배운 간격이 적용된다. 이 장면은 고치기 전 빌드와 견주지 않았다.

### 컴파일

- 처음 보는 셰이더는 창을 만들 때 160~172ms가 들었다(항등 172.3, focus 169.8, crt 172.3, 커서 160.1).
- 같은 셰이더로 다시 띄우면 0.4~1.1ms였다. Metal이 결과를 디스크에 캐시하는 것으로 짐작하고, 확인하지는 않았다.

## 판정

- 처음 이은 빌드는 기준에 걸렸다(메인 스레드가 10초에 9.3초 막힘). 미루기 판단이 얻기에서 막힌 간격을 배우게 고쳐(ADR-041) 0.2초로 줄였다. 고친 빌드는 기준 안이다.
- CPU는 움직이는 동안 코어 하나의 약 5%다. 기준(10%) 안이라 애니메이션 간격(8ms, Ghostty와 같음)은 그대로 둔다.

## 한계

- 한 기기(Apple M2 Pro 내장 화면)의 값이다. 외부 화면과 60Hz 화면은 재지 않았다.
- 화면이 왜 16.6ms마다 한 장씩 가져갔는지(ProMotion 동작으로 짐작)는 확인하지 않았다.
- 초점을 잃은 창의 셰이더(focus 셰이더의 붉은 기운)는 보지 못했다. 둘째 창을 띄워 초점을 옮기면 같은 자리에 떠서 첫 창을 가렸고, 가려진 창은 그리지 않는다(ADR-038). 창을 옮기거나 키·마우스를 흉내 내는 일은 하지 않았다.
- 투명 창, 분할한 창, 창 크기 바꾸기에서 셰이더는 보지 않았다.
- 셰이더가 움직이는 동안 키 입력 지연은 재지 않았다. 메인 스레드가 얻기에서 기다린 시간으로만 견줬다.
