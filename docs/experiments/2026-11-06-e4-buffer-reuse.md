# 실험 E4: 창 버퍼를 프레임마다 새로 잡지 않으면 올리기가 빨라지는가

- 날짜: 2026-11-06
- 관련 이슈: [#79](https://github.com/dj258255/b-terminal/issues/79), [실험 E3](2026-11-06-e3-present.md)
- 커밋: experiment/e4-buffer-reuse 브랜치(이 실험을 넣은 PR)
- 원자료: 아래 "결과"의 출력이 전부다

## 가설

> softbuffer(macOS)는 프레임마다 0으로 채운 새 버퍼(큰 창 약 11MB)를 잡는다. 실험 E3 뒤 이것이 약 2ms였다. Core Animation이 다 쓰고 돌려준 버퍼를 다시 쓰면 그만큼 줄어든다.

## 이 실험이 정할 것

> 줄어들면 vendor softbuffer에 버퍼 다시 쓰기를 남긴다. 아니면 되돌린다.

## 조건

- 기기: Apple Silicon Mac(arm64), macOS 26.3.1, release, 내장 화면, 창 1000×680pt(2000×1360px), `window-colorspace` 기본
- 내용: 실험 E2·E3과 같은 시계 스크립트(화면을 채운 뒤 한 줄만 0.25초마다), 한 번 띄울 때 약 58프레임
- 다시 쓰기: Core Animation이 그림을 놓을 때 부르는 release에서 버퍼를 버리지 않고 두고(같은 크기, 최대 3개), 다음 `buffer_mut`에서 꺼내 쓴다. `BT_E4_NO_REUSE` 환경 변수로 끄고 견줬다
- 두 조건을 번갈아 다섯 번씩 띄웠다

## 지표 정의

- 버퍼·옮기기·present·올리기까지: 실험 E3과 같다(프레임마다의 중앙값)

## 결과

| 회 | 새로 잡기: 버퍼 / 옮기기 / 올리기까지 | 다시 쓰기: 버퍼 / 옮기기 / 올리기까지 |
|---|---|---|
| 1 | 3.69 / 0.81 / 5.09ms | 0.00 / 2.81 / 3.19ms |
| 2 | 3.62 / 0.89 / 5.41ms | 0.00 / 4.24 / 5.18ms |
| 3 | 4.34 / 1.31 / 6.48ms | 0.00 / 4.60 / 5.48ms |
| 4 | 4.11 / 0.97 / 5.86ms | 0.00 / 4.64 / 5.61ms |
| 5 | 3.58 / 0.83 / 5.24ms | 0.00 / 3.77 / 4.67ms |

다섯 번의 올리기까지 중앙값: 새로 잡기 5.41ms, 다시 쓰기 5.18ms. 다섯 쌍 모두 다시 쓰기가 짧았다(0.23~1.90ms).

## 예상과 다른 점

- 버퍼 잡기는 0이 됐지만, **그 비용의 대부분이 옮기기(프레임 버퍼 → 창 버퍼 복사)로 옮겨 갔다**(0.8~1.3ms → 2.8~4.6ms). Core Animation이 넘겨받은 쪽을 쓰기 시 복사(copy-on-write)로 묶어, 다시 쓰는 버퍼에 처음 쓸 때 쪽 부재가 나는 것으로 짐작한다(가리지 않았다).
- 같은 조건 안에서도 실험 E3(버퍼 1.99ms, 올리기까지 2.70ms)보다 이번이 길다. 같은 날 다른 시각이라 시스템 부하로 짐작하며 원인을 가리지 않았다.

## 배제한 원인과 남은 가능성

- 버퍼를 0으로 채우는 비용: 다시 쓰기에서는 채우지 않는데도 옮기기가 늘어, 0 채우기보다 쪽 부재가 본 비용으로 보인다.
- 남은 가능성: IOSurface에 바로 그리거나 GPU로 올리면 복사와 쪽 부재를 함께 없앨 수 있다(이 실험의 범위 밖).

## 결론과 적용 범위

- 가설은 작게 맞았다: 다섯 쌍 모두 줄었지만 중앙값 차이는 약 0.2ms이고 쌍마다 0.2~1.9ms다. 버퍼 다시 쓰기를 남긴다(되돌릴 이유가 없고 매번 조금 빠르다).
- 올리기의 나머지(약 3~5ms, 대부분 옮기기)는 softbuffer 방식 안에서는 더 줄이기 어렵다.

## 다음에 확인할 것

- IOSurface 또는 Metal로 프레임을 올리는 비용.
- 시스템 부하가 낮을 때 같은 측정을 되풀이하기.
